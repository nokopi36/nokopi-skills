# MC オリジナル MOD 作成

アイデアから、動く MOD までを一緒に作る。
**基本方針: 小さく作って毎回動かす。** 仕様を固めてから 1 機能ずつ実装し、毎回ビルドとゲーム内確認を挟む。

## まず状態を判定する

作業フォルダを見て、どこから始めるか決める。

| 状態 | 開始フェーズ |
|---|---|
| 何もない | フェーズ 1 |
| `docs/SPEC.md` はあるがプロジェクト（`build.gradle`）がない | フェーズ 5 |
| プロジェクトと `docs/PROGRESS.md` がある | `PROGRESS.md` を読み、フェーズ 6 の続きから |

再開時は「前回は○○まで完了、次は△△」と一言で確認してから進む。

**実行環境の確認**: フェーズ 5 以降はローカルで Java（バージョンは `references/loaders.md` 参照）と git、bash が使える環境（Claude Code など）が必要。
シェルが使えない環境（claude.ai のチャットなど）では、フェーズ 4 まで進めて SPEC.md・refs.conf・CLAUDE.md を出力し、
「続きは Claude Code でこのスキルを使って」と案内して終える。

## フェーズ 1: アイデアの聞き取り

一度に全部聞かない。次の順で、答えに合わせて掘り下げる。
1. どんな MOD か一言で（例: 「畑を自動化する機械」「新しいボスと装備」）
2. 遊び方のイメージ — プレイヤーは何を集め、何を作り、何が楽しいのか。進行（序盤→終盤）はあるか
3. 似ている既存 MOD、好きな MOD（雰囲気や難易度の基準になる）
4. 一緒に遊ぶ MOD・モッドパックがあるか（バージョンと連携の判断材料）
5. 私的利用か公開予定か

アイデアが大きすぎる場合は、この段階で「最初に動かす最小の遊び（MVP）」を一緒に決める。
目安は **アイテム・ブロック合わせて 3〜5 個、仕組み 1 つ**。

## フェーズ 2: 類似 MOD の調査

CurseForge・Modrinth・GitHub で、アイデアのキーワードと似た MOD を検索する。
- 見つかったら、対応バージョン・機能・最終更新・ライセンスを伝える
- 「それを使えば足りる」ケースもあり得るので正直に伝え、作るなら差別化ポイントを一緒に考える
- ソースが公開されている類似 MOD は、**書き方の見本**として refs に入れる候補にする（コピーはしない）

## フェーズ 3: 環境の決定

- **バージョン**: 一緒に遊ぶ MOD があればそれに合わせる。なければ「最新」か「MOD が最も揃っているバージョン」かを聞く。
  最新状況は記憶でなく、ローダーの雛形リポジトリ（`scripts/resolve_ref.sh`）や主要 MOD の対応状況で確認する。曖昧な指定はパッチバージョンまで具体化する。
- **ローダー**: NeoForge／Fabric。一緒に遊ぶ MOD に合わせる。特に希望がなければ選択肢と違いを短く説明して選んでもらう。Forge は雛形が GitHub にないため `references/loaders.md` の注意を伝える。
- **連携 MOD**: 他 MOD の API を使う（アドオン）なら、その MOD のソースを refs に入れ、依存指定を調べる（`references/loaders.md` 4 章）。
- **mod_id**: 小文字英数字と `_`、2〜64 文字。既存 MOD と被らないか検索で確認。パッケージ名（例: `com.<作者名>.<mod_id>`）も決める。

## フェーズ 4: 仕様書

`assets/SPEC.template.md` を元に `docs/SPEC.md` を作る。
- 各機能に**具体的な数値**（耐久値、生成量、クールダウン、レシピ）を入れる。ユーザーが決めていない数値はバニラや類似 MOD を基準に提案し、**[仮]** を付けて後で調整できるようにする
- 機能を **MVP / 次 / いつか** に分ける。MVP 以外は実装しない
- 実装順と、各機能の完了条件（ゲーム内で何をすると何が起きれば OK か）を書く
- テクスチャ・音は誰が用意するか決める（ユーザーが描く／仮テクスチャで進める）。仮テクスチャは単色 PNG などで、差し替え前提

ユーザーに SPEC を確認してもらい、OK が出るまで次に進まない。

## フェーズ 5: 参考資料とプロジェクト作成

1. `refs.conf` を作る（形式は `scripts/setup_refs.sh` 冒頭）。基本はローダーの雛形、ローダーのドキュメント（対象バージョン部分のみ sparse）、連携 MOD、書き方の見本にする類似 MOD。
   SHA は `scripts/resolve_ref.sh <url> <branch>` で取得し、推測で書かない
2. `scripts/setup_refs.sh` をプロジェクトにコピーして実行し、`--verify` まで通す
3. `assets/CLAUDE.md.template` から `CLAUDE.md` を作る（`{{...}}` をすべて埋める）
4. `refs/<雛形>` から、`.git` を除いてプロジェクト直下にコピー。`gradle.properties` の `mod_id`・`mod_name`・`mod_group_id`・`mod_authors`・`mod_description`、パッケージ名、メインクラス名を変更し、雛形のサンプルコード（サンプルブロック等）は削除する。
   ライセンス欄は私的利用なら `All Rights Reserved`、公開予定ならユーザーに選んでもらう
5. **初めて `./gradlew` を実行する前に** `scripts/verify_gradle_wrapper.sh` を実行し、Wrapper が公式のものか検証する。失敗したら実行しない
6. `./gradlew build` が通ることを確認し、`git init` して最初のコミット（`refs/` は .gitignore 済み）
7. `assets/PROGRESS.template.md` から `docs/PROGRESS.md` を作る

## フェーズ 6: 1 機能ずつ実装

SPEC の実装順に、**1 回に 1 機能**。各機能で次のループを回す。

1. **計画を出して承認をもらう**: 作成・変更するファイル、使う API とその確認元（`refs/` のどのファイル）、SPEC から逸脱しそうな点
2. **実装**: API は記憶で書かず、`refs/` のドキュメントや見本コードで実在とシグネチャを確認してから使う。見つからなければ推測で埋めずにユーザーに伝える。
   書き方の対応表は `references/loaders.md` 5 章、機能別の参照先は `references/implementation.md`
3. **ビルド**: `./gradlew build` が通るまで直す
4. **テスト**: 数値・ロジックがあれば GameTest を書いて実行（`references/implementation.md` 参照）
5. **ゲーム内確認の手順を渡す**: `./gradlew runClient` で、何をクラフトし、どこに置き、何が起きれば正しいか。ユーザーに確認してもらう
6. **記録**: 確認が取れたら `docs/PROGRESS.md` を更新し、git コミット。SPEC から変えた点は SPEC を更新して `docs/DEVIATIONS.md` に理由を書く

ユーザーが遊んでみて「数値を変えたい」「やっぱりこうしたい」となるのは普通のこと。SPEC を先に直してから実装を直す。
MVP が全部終わったら、遊んだ感想を聞き、「次」の機能に進むか、調整するか決める。

### トラブル時
- ビルドエラーが 3 回直しても解決しない場合は、状況（エラー全文、試したこと）をまとめてユーザーに相談する
- `runClient` のクラッシュは `run/logs/latest.log` と `run/crash-reports/` を読んで原因を特定する
- 依存の追加・ビルド設定の変更は理由を説明してから行う

## フェーズ 7: 仕上げ（公開する場合のみ）

- 正式なテクスチャ・言語ファイル（`en_us.json` / `ja_jp.json`）の揃い具合を確認
- バージョン番号、`neoforge.mods.toml`／`fabric.mod.json` のメタデータ、ライセンス
- 配布先のルールを最新の状態で確認する。特に AI 利用: Modrinth は 2026-08 から AI 生成コードがかなりの部分を占める場合に申告が必須で、ほぼ AI のみで作ったものは検索に出ない。CurseForge はコードに関する規定なし（執筆時点）
- `./gradlew build` の成果物（`build/libs/*.jar`）を、まっさらな環境（ランチャーの新規プロファイル）で起動確認

## 参照ファイル
- `scripts/setup_refs.sh` / `scripts/resolve_ref.sh` — 参考資料の取得と SHA 解決（mc-mod-port と共通）
- `scripts/verify_gradle_wrapper.sh` — Gradle Wrapper の公式チェックサム照合
- `assets/SPEC.template.md` / `assets/CLAUDE.md.template` / `assets/PROGRESS.template.md`
- `references/loaders.md` — ローダー別の雛形・ドキュメントの所在、古い書き方との対応表
- `references/implementation.md` — 機能の種類ごとの参照先ドキュメントと実装時の注意
